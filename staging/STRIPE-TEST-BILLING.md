# Stripe test billing — Varga Cantieri 2.0

This candidate runs only with the localhost Firestore emulator and a synthetic Stripe signing secret. It uses the official Stripe SDK to verify raw signed snapshot events, with the pinned 2024-10-28.acacia payload contract. It never makes a Stripe network request, creates a Checkout session, registers an endpoint, charges a card, or sends a real invoice.

## Commercial contract

Existing catalog: Starter EUR 19.90, Professional EUR 39.90, Business EUR 79.90 for 30 days. The fixture accepts one fixed-price invoice line per subscription, one quantity, EUR, 30-day recurrence, no proration, discounts, extra lines, or out-of-band payment. A trusted server-side binding associates the exact subscription/customer with an approved tenant and tier. Only paid invoices advance the entitlement; event, invoice and billing-period IDs are recorded atomically and globally deduplicated. A failed payment does not extend access. Cancellation stops new grants and retains the already paid period. Out-of-order or incompatible invoices require reconciliation rather than silently granting time. Manual payment confirmation cannot override a Stripe-bound test tenant. Test receipts are marked as simulations, not tax invoices.

## Sandbox checkout candidate
`stripe-sandbox-checkout.mjs` now prepares an organization-owner checkout, validates the configured Stripe price, reserves a single durable attempt per tenant, uses a stable idempotency key and retrieves the stored session to bind the verified test subscription. Only emulator accounts with verified synthetic @example.test email addresses may use it. The Stripe SDK network adapter requires the explicit sandbox enable flag and a test secret; CI uses a local provider fixture instead. No secret is included. Manual confirmation and plan changes are blocked while a checkout is reserved. A successful checkout return alone cannot extend entitlement.

The separate local web purchasing portal in `staging/billing-web/` now includes synthetic owner login, company selection, plan cards, acceptance of simulation terms, checkout creation and a server-generated signed fixture invoice. It is not part of the iOS candidate or a public deployment. Run `node staging/billing-web/local-server.mjs` with the localhost Auth and Firestore emulators and the SDK dependencies installed. The portal binds only to 127.0.0.1:4173; the required demo owner and company must already exist in the emulator. No credit-card or real personal data is requested, no Stripe URL is exposed and no external payment calls are made. The in-memory fixture provider is intentionally disposable; interrupted attempts after a process restart remain locked pending reconciliation. The local simulation endpoint must never be exposed on a real or public billing server. A known unpaid Checkout session can now be canceled by the verified owner. The service requests expiration and re-reads the exact provider session; only a terminal expired, unpaid session with no subscription releases the reservation. An immutable expiration audit is written atomically, and the tenant may choose a new plan. Unknown or ambiguous sessions remain locked pending reconciliation. Paid or bound sessions cannot be cleared by this operation. Before external testing, complete recovery for unknown sessions and provider outages, verified subscription/invoice retrieval, durable handling of invoice events that arrive before checkout binding, and a real sandbox webhook receiver. Do not retry a stale checkout idempotency key.

## Before actual sandbox and production

- Confirm the business sells directly and exclusively to organizations for employees under Apple App Review 3.1.3(c), or implement the applicable in-app purchase / regional rules. Do not assume the enterprise exception applies to individual self-service sales. No Stripe purchasing button or external payment link has been added to iOS.
- Configure a separate Stripe sandbox with test-only credentials in secret storage; never place credentials in the repository or client. Replace the local fixture-only portal API with a reviewed sandbox-only server endpoint and actual hosted Stripe checkout; implement actual terms/cancellation UX. Prevent concurrent checkout and manual payment overlap.
- Pin and verify the actual Stripe API version and retrieve the authoritative invoice/payment intent/subscription before granting access; signed local fixtures are not a real sandbox end-to-end payment. Handle asynchronous payment completion, retry/reconciliation, invoice gaps, refunds, disputes, credit notes, tax, proration and plan changes. Avoid automatic destructive data removal on expiry.
- Confirm VAT-inclusive/exclusive pricing, billing details and Italian electronic invoicing/SDI obligations with a qualified tax professional. Stripe receipts and test invoice records are not a substitute for statutory invoices. No invoice emails or fiscal documents are generated.
- Add an authenticated server-only webhook endpoint, verified account separation, durable event queue, monitoring, rate limits and secrets management; test actual Stripe sandbox before any real charge or deployment. Keep original V1 and production Firebase untouched.

References: https://developer.apple.com/app-store/review/guidelines/ (3.1.1, 3.1.3(c)); https://docs.stripe.com/billing/subscriptions/webhooks ; https://docs.stripe.com/webhooks .

## Owner-configured Sandbox catalog

The three owner-supplied 30-day price identifiers are recorded in `stripe-sandbox-catalog.mjs`. The checkout defaults to this catalog; all automatic tests still use local fixtures and never reach Stripe. The opt-in `audit_stripe_sandbox` workflow input on the staging branch enables a separate read-only audit job. Before dispatch, create the dedicated GitHub environment `stripe-sandbox-readonly`, limit deployment branches to `varga-cantieri-v2-staging`, and add its environment secret `VARGA_STRIPE_SANDBOX_READ_KEY` using a restricted `rk_test_` Stripe key with Prices read permission only (Products read only if required by Stripe). Do not use a repository-wide secret or expose the key in chat. The job checks each price ID, lookup key, EUR amount, recurrence and test-mode status; it performs no Stripe writes. No account audit has run yet. The broader checkout connection and webhook verification remain separate steps.
