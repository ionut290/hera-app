# OCI shared radio host — deployment candidate (not deployed)

Owner selected existing radio-romanii-italia OCI VM. Run shared-host-preflight.sh first, inspect available memory, CPU/load, free disk and active services. API/DB resource caps are initial conservative limits (0.5/0.75 CPU, 512 MiB/1 GiB RAM). Never stop, restart, update or reconfigure radio or legacy VARGA services. No host package installation or firewall/proxy edits without a separate reviewed step.

## Network
Keep existing host and network untouched; public HTTPS only after a separate reviewed DNS/TLS and reverse-proxy change. Never expose 5432 or 8080. Docker publishes only host loopback 18084; PostgreSQL network internal. Use a dedicated hostname, not the radio domain. Caddy example is not enabled. Configure API ingress rate limiting (particularly join-code guesses), allowed browser/native origins and authentication testing before public access. Never put credentials in the repo or Docker build context.

## Secrets and local startup
Use existing Docker Engine/Compose; do not upgrade shared host packages. Clone the exact reviewed Oracle branch commit. Create an absolute secret directory outside checkout with restricted access. Generate two independent >=32-character random hex passwords (db-owner-password and app-db-password). Create app-database-url containing postgresql://varga_app:<app password>@db:5432/varga_v2_oracle (hex avoids URI escaping). Supply a narrowly scoped, explicitly authorized Firebase V2 staging credential file firebase-credentials.json, NOT V1 or radio. Container node UID 1000 must be able to read its two mounted secret files; PostgreSQL image user must be able to read its own secrets. Restrict directory traversal and file ownership/permissions appropriately; never make keys world-readable. Credential provisioning is intentionally not automated. Set VARGA_SECRETS_DIR to the absolute directory. Run docker compose -f compose.yml config --quiet, then docker compose -f compose.yml up -d --build. First initialization applies both migrations and creates limited role. On partial init failure, inspect logs; never delete existing volumes or retry by resetting data. Future schema changes require a separate migration procedure. Verify DB schema, server health, real Firebase token/revocation and tenant isolation with synthetic test accounts before TLS/public use. Do not copy production data.

## Backup
Set VARGA_BACKUP_DIR to a private absolute directory outside checkout. Run bash backup.sh on the shared host. It makes a custom-format pg_dump and checks archive contents; it never replaces an existing backup or deletes older files. Encrypt and copy off-host, set retention, schedule and test restoring in a separate database. A local dump alone is not disaster recovery. No Object Storage or automatic retention configured yet.

## Limitations
Container build currently pins direct npm dependencies but does not yet include a lockfile; resolve and audit transitive dependencies before production deployment. HTTPS template is a starting point, not a complete production ingress policy. Server remains a prototype; real credentials, DNS, rate limits, cross-origin/native access and rollback are unverified. No OCI resource created by these files. Never execute against V1, V2 Firestore or radio.
