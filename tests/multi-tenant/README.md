 # Prototipo isolamento aziende (solo emulator)

Non integrare né distribuire queste regole su Firebase reale. Il progetto demo è fittizio, l'unico host consentito è 127.0.0.1:8180. Usare un checkout temporaneo del branch, Node 22, Java compatibile con Firestore Emulator, Firebase CLI e @firebase/rules-unit-testing compatibile con Firebase 11.10.0. Installare dipendenze di test solo nel checkout temporaneo, senza aggiornare package.json o lockfile di produzione. Dal root del checkout, eseguire:

```sh
npm ci
npm install --no-save --package-lock=false @firebase/rules-unit-testing@4 firebase-tools@14 firebase-admin@13
npx firebase emulators:exec --only firestore,auth --project demo-varga-multi-tenant --config tests/multi-tenant/firebase.emulator.json 'node tests/multi-tenant/isolation.test.cjs && node tests/multi-tenant/tenant-service.emulator.test.cjs && node tests/multi-tenant/auth-adapter.emulator.test.cjs'
```

Il test cancella soltanto i dati sintetici dell'emulatore locale dedicato. Non utilizzare un emulatore condiviso. Le 17 asserzioni riguardano il prototipo di appartenenza aziendale; non certificano l'app completa. Prima suite di 17 asserzioni superata su GitHub Actions (run 45600354265). La suite estesa va verificata separatamente. Per il piano di sviluppo vedere docs/MULTI_AZIENDA_V2.md.

## Provisioning e inviti (prototipo backend)
La logica in tenant-service.prototype.cjs non è esportata dalle Functions esistenti. Il super amministratore può creare un tenant e un owner; l'owner invita ruoli operativi e admin, un admin soltanto ruoli operativi. Gli inviti sono legati a tenant ed email verificata, con token casuale monouso memorizzato come hash, validità di 7 giorni e accettazione atomica. Nessuna membership esistente è sovrascritta. Il backend futuro dovrà verificare i token Firebase e la revoca, risolvere l'identità del proprietario tramite Admin Auth, applicare rate limiting e idempotenza alle richieste di provisioning/invito, gestire revoca e sospensione con aggiornamento dell'indice personale, trasmettere gli inviti in modo sicuro, e registrare audit senza token. Non esiste ancora un endpoint, UI di registrazione reale, invio email o progetto staging online. I sette giorni e la creazione aziende riservata al super admin sono scelte iniziali modificabili. La verifica di sicurezza completa richiede anche Storage, integrazioni e cache.

## Pannello Super Admin (fase sperimentale)
- super-admin-demo.html: interfaccia offline con ricerca, filtro, creazione simulata, sospensione/riattivazione confermata e registro attività. Nessun dato reale o persistenza. L'amministratore mostrato è un esempio, non un dato backend.
- platform-admin.prototype.cjs: elenco paginato dei soli metadati aziendali per super admin; cambio stato con motivazione e audit atomico, senza cancellazioni o modifiche di membership. La sospensione blocca i controlli di accesso del prototipo, non elimina record. Ogni cambio stato incrementa inviteGeneration, invalidando gli inviti precedenti. L'indice personale può rimanere obsoleto: il selettore reale deve verificare lo stato autorevole del tenant, mai fidarsi della cache.
- Il servizio non è esposto via rete e non è integrato nella UI. Il futuro adapter deve verificare token e revoca, App Check ove applicabile, limitazione richieste e autorizzazione a ogni operazione. La sospensione effettiva su tutti i dati, cache offline e integrazioni richiede ulteriori controlli. Gestione/trasferimento del ruolo owner non implementati; non consentire la perdita dell'ultimo owner.
- Test estesi: elenco/paginazione, accesso negato ai non super admin, sospensione con audit, nessuna perdita di membership, riattivazione senza riutilizzare vecchi inviti. La suite precedente relativa agli inviti è passata nel run 45600654317; verificare separatamente la nuova suite.

## Collegamento Firebase Auth locale
Il nuovo adapter collega i servizi tenant e platform admin ai token emessi dall'emulatore Auth. Verifica il token con controllo revoca, consulta l'utente corrente, richiede email verificata e ricontrolla il claim amministratore. Gli identificativi del proprietario vengono risolti da Auth; i ruoli nel payload non sono attendibili. Il test crea esclusivamente account sintetici e usa Auth 127.0.0.1:9199 e Firestore 127.0.0.1:8180 nel progetto demo. L'adapter rifiuta avvio fuori da questi emulatori. Non è un endpoint pubblico o un collegamento al database di produzione. Restano da sviluppare endpoint autenticati di staging, App Check, rate limiting, idempotenza, invio inviti sicuro, interfaccia collegata e regole complete dei dati operativi. La suite Super Admin precedente è passata nel run 45601208259; verificare separatamente i nuovi test Auth.
